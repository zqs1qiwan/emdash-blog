# 博客文章写法（科普口吻 + 严谨结构）

适用：`blog.laobaitv.net` 上任何面向公众的技术/安全/产业类文章。目标读者 = 普罗大众（要能读下去）+ 工程师（要能读到细节）。

## 一、口吻规则

- 开头从**事件本身**切入：谁在什么时间做了什么、为什么和普通读者有关。不要以“我维护的站点”开场。
- 自己的站点/项目只能作为**研究样本**出现：“笔者维运的一个站点……”，后面跟数据与方法。禁止“本站如何如何”“我们的站被扫了 N 次”这类站点汇报句。
- 术语先解释再使用：一段日常语言讲清（例：PHP 是服务器生成网页的语言；RCE 是让服务器替你跑任意代码；webshell 是藏进网站的后门脚本），技术细节另起一节。
- 技术节里可以直接上细节（版本号、函数名、请求生命周期），但每段先给一句“这意味什么”，再给机制。
- 不用营销词，不用感叹号；结论先行，数据说话。

## 一·五、标题即观点

- 标题本身要能传达一个判断，读者只看标题就知道文章的立场。
- 不用「XX 核验」「XX 复盘」「XX 调研」这类只描述动作的标题；把判断写进标题。
- 例：「四家补丁撞在同一周，但排期的是日历，不是黑客」优于「黑色星期三核验：到底发生了什么」——前者已经给出结论，后者只是承诺要查。
- 正文结构跟着标题的论点走：每节一个小论点（「一张日历，解释了大部分巧合」「Node.js：八个月的时间差，才是这周最被低估的故事」），不是「第一部分/第二部分」。

## 二、九段结构（按顺序）

1. **导语**：发生了什么 + 为什么与你有关 + 本文讲哪几件事（一句话列清）。
2. **科普基础**：概念、规模数字（带来源与口径）、为什么这类问题严重。
3. **技术细节**：根因、为何常规防护无效、受影响范围、修复方式与生效条件。
4. **时间线**：用列表按时间点排，标注时区；突出“窗口有多短”。
5. **案例数据**：样本说明 + 口径声明（采样/不可见项）+ 数字列表 + 全部落空的验证结果。先声明局限，再给结论。
6. **可疑/争议分析**：按小时/按天的曲线 → 观察到什么 → **明确写出“不能证明什么”**（看不到请求体、样本无目标组件等）→ 行业侧证据 → 得出的默认假设。
7. **谁做得好**：3–6 个角色，每个一行论断标题 + 做了什么（有来源）+ 为什么重要。只写能引用的动作，不替厂商编反应。
8. **威胁与机遇**：4–6 个方向，每个四件套：
   - 可观察到的事实（带来源）
   - 判断（明确标为判断）
   - 可引用量级（市场规模/拦截率/占比，标机构与年份）
   - 对小团队或读者的含义
9. **行动清单 + 结语**：按角色分组（个人站长 / 企业运维 / 托管商 / 普通用户），每条可执行；结语给“技术/节奏/产业”三层收束。

文末附图片来源与主要参考（机构名 + 链接）。

## 三、严谨性清单（发布前逐条过）

- [ ] 每个厂商/机构的动作都有链接或明确出处；查不到的动作删掉，不写“据说/业内普遍”。
- [ ] 市场数字带口径（机构 + 年份 + 定义），并说明是预测还是实测。
- [ ] 观察与判断分句；推断用“判断/意味着”，不用“证明”。
- [ ] 数据局限写明：采样、盲区（请求体不可见）、样本不代表全局。
- [ ] 历史类比只用有出处的案例，时间差写清楚（次日 / 当天 / 数小时）。
- [ ] 标题给出判断，不用「核验/复盘/调研」这类动作词，也不用「史上最严重」这类无法支撑的定语。
- [ ] HTML 源文件中零 `**`、`__` 等 markdown 标记，强调一律用 `<strong>`/`<em>`/`<code>`。转换器只做 HTML→Portable Text，不解析 markdown，`**` 会原样印在正文里。
- [ ] 线上可见文本的星号计数已核：`**` 必须为 0；技术语境里的单个 `*`（`wp-*`、`*.php` 通配符）属正常，不要「修」。

## 四、配图

- 每篇一张封面即可；新闻媒体图必须写来源行（“图片来源：<媒体> 报道配图”），不确定版权时优先用 Wikimedia Commons（CC/GPL/PD）并在图注署名。
- 换图 = 三处同步：R2 对象（`--remote`）、`media` 表行、`ec_posts.featured_image` JSON；完成后清理旧 media 行与旧 R2 对象。
- 图片尺寸按 16:9 或 21:9 横幅裁切，webp 质量 80–85，控制在 100KB 内。

## 五、常见失败模式

| 失败 | 症状 | 规避 |
|---|---|---|
| 写成站点汇报 | 读者不知道“这跟我有什么关系” | 开头从事件切入，站点只作样本 |
| 编造厂商反应 | “某托管商 4 小时完成升级”类无源句 | 只写有链接的动作，删掉推测 |
| 表格丢失 | 上线后整节不见、无报错 | 源码用列表，不用 `<table>` |
| 编码垃圾 | 混入西里尔/日文碎片 | 转换前跑垃圾扫描 grep |
| 只有威胁没有机遇 | 缺少“谁做得好/市场方向” | 按九段结构验收 |
| 数据越界 | 把时间重合写成“已证实利用” | 明确写“不能证明” |
| markdown 混入 HTML | 正文出现裸 `**`、`*` | 源文件只写 HTML 标签；发布后用可见文本断言星号计数 |
| 汇报腔标题 | 「XX 核验/复盘/调研」 | 标题写成判断句 |

## 六、发布后校验（HTTP 200 不算通过）

- 改已发布文章（`UPDATE ec_posts SET title/excerpt/content ... WHERE id=...`）后，200 只能证明页面没崩，证明不了内容换没换。必须抓页面做**可见文本断言**：去 `script`/`style` → 去标签 → 反转义 → 压空白，然后断言 ① 新版开头那句话在；② `**` 计数为 0；③ h2 数量与草稿对得上。

```python
body = re.sub(r'<(script|style)[^>]*>.*?</\1>', ' ', raw, flags=re.S)
txt = re.sub(r'\s+', ' ', html.unescape(re.sub(r'<[^>]+>', ' ', body)))
assert txt.count('**') == 0
assert '新版开头那句话' in txt
```

- UPDATE 按 post id 是**幂等**的：线上与草稿不符时重跑同一条 SQL，不要手工改 D1 里的 content。
- 动笔前先实测线上现状（开头句、星号计数、h2 列表）。同一篇文章可能被多轮改写，也无法凭「上一轮已经发过」的说法判断——线上究竟是哪一版，只有抓页面说了算。
- 快速探针连续打会产生瞬态 TLS 失败（SSL UNEXPECTED_EOF），重试一次即可，不要当成站点故障。
